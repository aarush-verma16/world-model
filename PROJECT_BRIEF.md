## 1. Project Overview

We are building a Dreamer-style world model: an agent that learns a compressed, predictive
model of its environment (the "world model") and trains its decision-making policy almost
entirely inside imagined rollouts generated by that model, rather than through direct
trial-and-error in the real environment.

**Environment:** Crafter (`CrafterReward-v1`), a 64x64 pixel-observation survival game used as
the reference benchmark in the DreamerV3 paper. Chosen because it requires long-horizon
reasoning and tool use, published baseline numbers exist for direct comparison, and it is cheap
enough to run on a single workstation.

**Research goal:** this is not a novel-architecture paper. It is a faithful, small-scale
implementation of the Dreamer/RSSM recipe, followed by a controlled ablation study under a
fixed compute budget (the specific axis — latent size, imagination horizon length, or
latent-space vs. representation-space prediction — will be chosen after the baseline is
working, based on what the baseline actually shows). The end deliverables are: a working,
documented open-source implementation; an ablation result; a short paper; a public docs site.

**Non-goals:** no API calls to any external model or service anywhere in the training or
inference path (Cursor itself is the only external tool in the loop — everything the agent
runs, trains, or predicts with must be local). No attempt to match full DreamerV3 scale or
compute. No scope creep into multi-environment generalization — Crafter only.

## 2. Hardware & Runtime Constraints

- Windows desktop: AMD CPU, NVIDIA GeForce RTX 5080 (16 GiB GDDR7, Blackwell /
  sm_120), 32 GiB system RAM, 2 TB SSD.
- PyTorch runs on **CUDA**. RTX 50-series requires a CUDA **12.8+** build
  (`pip install torch torchvision --index-url https://download.pytorch.org/whl/cu128`).
  The default PyPI torch wheel is CPU-only on Windows and will silently skip
  the GPU.
- Verify `torch.cuda.is_available()` returns `True` before any training work.
  Mixed precision is **bf16 AMP** (native on this card, no GradScaler). TF32
  matmuls and cuDNN autotune are on (`training.device.configure_runtime`).
- VRAM budget is 16 GiB dedicated; the Windows desktop already uses ~1.5 GiB.
  Replay lives in system RAM. Default world-model train config is batch 16 ×
  seq 32 + bf16 AMP (4× the Mac swap-safe batch). seq 64 is the DreamerV3
  default but filled this card in a smoke test — only bump it if nvidia-smi
  shows headroom. If a step OOMs, drop `batch_size` 16 → 8. Do not shrink
  the 32×32 categorical latent.

## 4. Architecture Specification

The system has two trainable parts trained on two different signals: the **world model**
(trained via self-supervised prediction on real replayed experience) and the **actor-critic**
(trained on imagined rollouts generated by a frozen copy of the world model).

### 4.1 World Model Components

**Encoder** — CNN, maps a 64x64x3 real observation to an embedding vector. Standard conv
stack (e.g. 4 conv layers, stride 2, increasing channels), no pooling, ReLU or SiLU activations.

**RSSM (Recurrent State-Space Model)** — the core. Maintains two state components per timestep:
- **Deterministic state `h`**: produced by a GRU cell, carries memory across time.
- **Stochastic latent `z`**: **discrete categorical**, not continuous Gaussian (DreamerV2/V3
  design choice — trains more stably). Default: 32 categorical variables x 32 classes each
  (DreamerV3 standard; do not shrink this for VRAM — drop batch/seq instead). Use
  straight-through gradient estimation for backprop through the discrete sampling step.
- Two ways to compute `z` at each step — **must be named explicitly and never conflated**:
  - `z_posterior`: computed from `h` **and** the real observation's encoder embedding (used
    during world-model training, when real data is available).
  - `z_prior`: computed from `h` **alone**, no observation (used during imagination rollouts).

**Decoder** — CNN, reconstructs the 64x64x3 image from `[h, z]`. Reconstruction loss is a
training signal only — decoded images are not needed at inference/imagination time.

**Auxiliary heads** (small MLPs off `[h, z]`):
- Reward predictor — critical, since this is what lets the actor-critic evaluate imagined
  trajectories without ever touching the real environment.
- Continue/discount predictor — predicts episode termination (e.g. death in Crafter).

**World model loss** = image reconstruction loss + reward prediction loss + continue
prediction loss + KL divergence between `z_prior` and `z_posterior`, with **KL balancing**
(asymmetric weighting of the two KL directions, per DreamerV2/V3) to prevent posterior
collapse. If imagined rollouts diverge wildly from real behavior after a few steps, KL
balancing is the first thing to check.

### 4.2 Actor-Critic Components

- **Actor**: MLP policy operating on `[h, z]`, outputs an action distribution.
- **Critic**: MLP value function operating on `[h, z]`, trained with lambda-returns computed
  over imagined trajectories.
- Trained **entirely on imagined rollouts**: starting from a real latent state, the world
  model (frozen during this phase) is rolled forward N steps (default 15) using `z_prior` only
  — no encoder, no real observations — with the actor choosing actions at each imagined step.
  The resulting chain of predicted rewards is used to compute returns and backprop directly
  into actor and critic weights (the whole rollout is differentiable).
- Apply DreamerV3-style return normalization (percentile-based scaling) so the actor-critic
  loss stays stable.

### 4.3 The Outer Training Loop

```
1. Act in the real environment with current policy -> collect real (obs, action, reward) data into replay buffer
2. Train world model (encoder, RSSM, decoder, heads) on real replay data (supervised, self-supervised style)
3. Freeze world model -> generate imagined rollouts from real latent states -> train actor-critic on them
4. Return to step 1 with the updated policy, collect more (better-targeted) real data
5. Repeat
```

### 4.4 Tensor Convention

**All tensors are `[batch, time, features]`** unless explicitly stated otherwise in a docstring
or variable name. Always name variables to disambiguate prior vs. posterior (`z_prior_t`,
`z_post_t`, never just `z_t`). This convention must be followed consistently — it is the most
common source of subtle bugs in RSSM implementations.

## 6. Git Workflow

- Work and push **directly on `main`** — no feature branches.
- Prefer small, frequent commits with why-focused messages (e.g. "RSSM: switch to discrete
  categoricals after Gaussian posterior collapse"). The commit history is raw material for
  the paper method section and the docs experiment log later.
- Keep `main` working; do not push known-broken code.
- Tag milestones on `main`: `v0.1-encoder-working`, `v0.2-rssm-working`,
  `v1.0-baseline-result`, `v2.0-ablation-complete`.
- `.gitignore` all checkpoints and replay buffer dumps unless tracked via Git LFS.
